## 1. 设计目标

后端负责身份认证、团队与小组组织管理、项目管理、任务协作、甘特图排期读写，以及所有服务端权限校验。前端原型中的工作台统计、项目列表、任务列表、甘特图、登录注册、超管后台和个人设置都由本 API 提供数据。

项目最终部署到 Cloudflare Workers，因此 V1 后端按无服务器、Web API、D1 binding、Wrangler migration 的方式设计，不依赖常驻进程、内存会话、文件系统写入或传统数据库连接池。

V1 不实现任务操作历史、密码找回、评论、附件、任务依赖、通知发送和成员视图。这些能力保留扩展点，但不提前污染 MVP 接口。

## 2. Cloudflare 架构

### 2.1 部署形态

```text
Browser / Cloudflare Pages static assets
        |
        v
Cloudflare Worker API
        |
        +-- D1 binding: env.DB
        +-- KV binding: env.RATE_LIMIT_KV（可选，登录/写接口限流）
        +-- Worker secrets: SESSION_SECRET / PASSWORD_PEPPER（可选）
        +-- Cron Trigger: 清理过期会话和软删除数据
```

前端可部署在 Cloudflare Pages，也可由同一个 Worker 托管静态资源。API Worker 统一处理 `/api/v1/*` 路由。

### 2.2 推荐技术栈

| 层 | 建议 |
| --- | --- |
| Runtime | Cloudflare Workers module worker |
| 路由 | Hono |
| 校验 | Zod + `@hono/zod-validator` |
| 数据访问 | D1 prepared statements；复杂查询先手写 SQL |
| 密码哈希 | WebCrypto PBKDF2-SHA256 或 Workers 可用的 Argon2/WASM；V1 需在实现前压测 CPU 成本 |
| OpenAPI | `api-docs.yaml` 作为源文档，可导入 Swagger UI / Apifox |
| 部署 | `wrangler deploy`，staging/production 分环境 |

说明：Workers 不适合依赖 Node 原生模块。选择密码库和 ORM 时必须确认可在 Workers runtime 运行。

## 3. D1 数据模型落地

现有数据库设计文档以 MySQL 8.0 为基准。部署到 Cloudflare Workers 后，生产实现建议将建表脚本转换为 D1/SQLite 版本：

| MySQL 设计 | D1 落地 |
| --- | --- |
| `BIGINT UNSIGNED AUTO_INCREMENT` | `INTEGER PRIMARY KEY AUTOINCREMENT` |
| `DATETIME` | `TEXT`，存 ISO 8601 UTC |
| 任务起止时间 | `TEXT`，存本地 `YYYY-MM-DDTHH:mm`，分钟为 `00` / `30` |
| `ENUM` | `TEXT CHECK (field IN (...))` |
| `VARCHAR(n)` | `TEXT CHECK (length(field) <= n)` |
| `ON UPDATE CURRENT_TIMESTAMP` | 应用层更新 `updated_at` |
| `CHECK` | D1/SQLite `CHECK`，复杂跨表规则仍由服务层事务保证 |

建议新增 `migrations/0001_initial.sql` 作为 D1 权威脚本，保留 `数据库设计文档.md` 作为逻辑设计。

关键 D1 表结构示意：

```sql
CREATE TABLE users (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  username TEXT NOT NULL UNIQUE CHECK (length(username) BETWEEN 2 AND 32),
  email TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  system_role TEXT NOT NULL DEFAULT 'member' CHECK (system_role IN ('super_admin', 'member')),
  failed_login_count INTEGER NOT NULL DEFAULT 0,
  locked_until TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE tasks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id INTEGER NOT NULL,
  group_id INTEGER NOT NULL,
  title TEXT NOT NULL CHECK (length(title) BETWEEN 1 AND 200),
  detail TEXT CHECK (detail IS NULL OR length(detail) <= 10000),
  assignee_id INTEGER NOT NULL,
  start_date TEXT,
  end_date TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'todo' CHECK (status IN ('todo', 'in_progress', 'done')),
  priority TEXT NOT NULL DEFAULT 'medium' CHECK (priority IN ('low', 'medium', 'high', 'urgent')),
  completed_at TEXT,
  created_by INTEGER NOT NULL,
  deleted_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK (start_date IS NULL OR start_date <= end_date),
  CHECK ((status = 'done' AND completed_at IS NOT NULL) OR (status <> 'done' AND completed_at IS NULL)),
  FOREIGN KEY (project_id) REFERENCES projects(id),
  FOREIGN KEY (group_id) REFERENCES team_groups(id),
  FOREIGN KEY (assignee_id) REFERENCES users(id),
  FOREIGN KEY (created_by) REFERENCES users(id)
);
```

核心索引保持不变：

```sql
CREATE INDEX idx_group_members_user ON group_members(user_id);
CREATE INDEX idx_tasks_project_group ON tasks(project_id, group_id);
CREATE INDEX idx_tasks_assignee ON tasks(assignee_id, status);
CREATE INDEX idx_tasks_end_date ON tasks(end_date);
CREATE INDEX idx_sessions_expires ON sessions(expires_at);
```

## 5. 统一 API 契约

### 5.1 响应格式

成功响应：

```json
{
  "data": {},
  "meta": {
    "requestId": "req_01J...",
    "pagination": null
  }
}
```

错误响应：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数校验失败",
    "details": [
      { "field": "endDate", "reason": "结束时间为必填项" }
    ]
  },
  "meta": { "requestId": "req_01J..." }
}
```

### 5.2 认证方式

优先使用 HttpOnly Cookie：

```text
Set-Cookie: welo_session=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=1209600
```

同时支持 `Authorization: Bearer <token>`，便于非浏览器客户端和接口调试。

会话 token 使用高熵随机值。数据库推荐存 token hash，而不是明文 token：

```text
token -> SHA-256(token) -> sessions.token_hash
```

### 5.3 分页与筛选

列表接口默认 `page=1&pageSize=20`，`pageSize` 最大 100。排序字段必须使用白名单映射，禁止直接拼接客户端传入的 SQL 字段。

任务筛选：

```text
groupId, assigneeId, status, priority
startDateFrom, startDateTo, endDateFrom, endDateTo
keyword, sortBy=endDate|createdAt|priority, sortOrder=asc|desc
```

## 6. 错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 参数格式、长度、日期区间、枚举错误 |
| 401 | `UNAUTHENTICATED` | 未登录或会话过期 |
| 401 | `INVALID_CREDENTIALS` | 用户名/邮箱或密码错误 |
| 403 | `FORBIDDEN` | 已登录但无操作权限 |
| 404 | `NOT_FOUND` | 资源不存在、已删除或当前用户不可见 |
| 409 | `CONFLICT` | 唯一键冲突、成员仍有关联任务 |
| 409 | `VERSION_CONFLICT` | 甘特图保存时数据已被其他请求更新 |
| 423 | `ACCOUNT_LOCKED` | 登录失败达到 5 次后的锁定期 |
| 429 | `RATE_LIMITED` | 请求过于频繁 |
| 500 | `INTERNAL_ERROR` | 未预期错误 |

受权限保护的详情、更新和删除接口，对“资源不存在”和“资源不可见”统一返回 `404`，避免探测其他小组或团队的数据。

## 7. 权限模型

### 7.1 AuthContext

每个受保护请求都从会话解析出：

```text
AuthContext {
  userId: string
  systemRole: "super_admin" | "member"
  sessionTokenHash: string
  requestId: string
}
```

角色以 D1 中的 `users.system_role` 为准，禁止信任前端传入的角色、团队或小组权限。

### 7.2 权限规则

1. 超级管理员拥有全局读写权限；
2. 普通人员必须属于项目所在团队，才可查看项目基本信息；
3. 普通人员查看任务时，必须属于任务所在小组；
4. 普通人员可以在所属团队创建项目；
5. 普通人员可以在所属团队项目中创建任务，但任务小组必须是该团队内启用小组；
6. 普通人员可以修改自己可见的任务和拖拽排期；
7. 普通人员不可删除任务，不可编辑、归档、删除项目，不可管理团队、小组和成员；
8. 归档团队、归档项目只读；
9. 停用小组保留历史任务，但不可创建新任务；
10. 任务负责人必须属于任务小组。

### 7.3 核心可见性 SQL

普通成员任务查询必须把权限写入 SQL：

```sql
SELECT t.*
FROM tasks t
JOIN projects p ON p.id = t.project_id AND p.deleted_at IS NULL
JOIN team_groups g ON g.id = t.group_id AND g.team_id = p.team_id
JOIN team_members tm ON tm.team_id = p.team_id AND tm.user_id = ?
JOIN group_members gm ON gm.group_id = t.group_id AND gm.user_id = ?
WHERE p.team_id = ?
  AND t.project_id = ?
  AND t.deleted_at IS NULL
ORDER BY t.end_date ASC
LIMIT ? OFFSET ?;
```

超管可省略 `team_members` 和 `group_members` 条件，但仍需保留团队、项目和软删除条件。

## 8. 事务与一致性

D1 支持批量语句和 SQL 事务语义，但 Worker 是无状态运行环境，不能依赖进程级锁。所有跨表业务规则必须在写入前查询校验，并在同一次请求中完成写入。

### 8.1 创建任务

1. 读取项目，确认属于路径中的 `teamId`、未删除、状态为 `active`；
2. 读取小组，确认属于项目团队、状态为 `active`；
3. 校验操作者创建权限；
4. 校验负责人属于该小组；
5. 校验标题、详细内容、日期、状态、优先级；
6. 插入任务；若状态为 `done`，写入当前 UTC `completed_at`；
7. 返回带负责人和小组信息的任务 DTO。

### 8.2 更新任务

普通人员先用可见性 SQL 加载任务，超管按资源存在性加载任务。更新小组或负责人时重新校验“任务小组属于项目团队”和“负责人属于任务小组”。

状态变更为 `done` 时写 `completed_at=now`；从 `done` 回退时清空 `completed_at`。V1 允许回退但不要求原因；V1.1 再接入 `task_logs`。

### 8.3 甘特图拖拽保存

接口：`PATCH /teams/{teamId}/projects/{projectId}/tasks/{taskId}/schedule`

请求体：

```json
{
  "startDate": "2026-09-10T09:30",
  "endDate": "2026-09-15T18:00",
  "expectedUpdatedAt": "2026-09-07T08:30:00Z"
}
```

服务端使用乐观并发控制：

```sql
UPDATE tasks
SET start_date = ?, end_date = ?, updated_at = CURRENT_TIMESTAMP
WHERE id = ?
  AND project_id = ?
  AND deleted_at IS NULL
  AND updated_at = ?;
```

更新行数为 0 时返回 `409 VERSION_CONFLICT`，前端按产品要求回滚并重新拉取数据。无开始时间的任务在甘特图 DTO 中返回 `renderStartDate=endDate`、`isVirtualStart=true`，但不写回 `start_date`；只有拖拽成功后才保存真实开始日期。

### 8.4 移出成员

移出团队前必须确认：

1. 用户已从该团队所有小组移出；
2. 用户在该团队下没有未软删除的负责中任务；
3. 若仍有关联，返回 `409 MEMBER_HAS_ASSIGNMENTS`。

后端不自动改写历史任务负责人，避免静默破坏审计链路。

## 10. 工作台与甘特图数据

### 10.1 工作台

`GET /teams/{teamId}/dashboard` 返回：

```json
{
  "inProgressProjectCount": 6,
  "visibleTaskCount": 42,
  "myOpenTaskCount": 8,
  "overdueTaskCount": 2,
  "upcomingDeadlineCount": 3,
  "recentProjects": [],
  "upcomingDeadlines": []
}
```

所有任务统计都必须复用可见性 SQL。普通人员只能统计可见任务；超管统计当前团队全部任务。

### 10.2 甘特图

`GET /teams/{teamId}/projects/{projectId}/gantt?granularity=day` 返回：

```json
{
  "project": {},
  "range": {
    "startDate": "2026-09-04T00:00",
    "endDate": "2026-09-20T00:00",
    "granularity": "day"
  },
  "tasks": []
}
```

范围计算：对可见任务取最早有效开始日期和最晚结束日期，前后各扩展 3 天。`startDate=null` 的任务用 `endDate` 参与范围计算，并在 DTO 中标记 `isVirtualStart=true`。

## 11. 安全与限流

1. 密码、Cookie、Authorization、数据库绑定信息不得写入日志；
2. 登录按 IP + account 双维度限流；
3. 写接口按 userId 限流；
4. Cookie 认证的非 GET 请求校验 CSRF token；
5. 生产环境只允许 HTTPS；
6. CORS 使用域名白名单，不使用 `*` 搭配凭证；
7. 响应对象使用白名单字段，永不返回 `password_hash`、失败登录计数、锁定字段和 token hash；
8. 通过 Cloudflare Observability 记录 requestId、路径、状态码、耗时和错误码。

## 12. 定时任务

Worker Cron 每 30 分钟执行：

1. 删除过期 `sessions`；
2. 物理清理超过 30 天恢复窗口的软删除任务和项目；
3. 输出清理数量和耗时日志。

清理 SQL 必须分批执行，避免一次请求处理过多行。

## 13. 测试与验收

| 类别 | 必测场景 |
| --- | --- |
| 认证 | 注册唯一性、邮箱小写、密码错误统一提示、连续 5 次锁定、过期会话 |
| 权限 | A 组看不到 B 组任务；双组看到并集；不可见详情返回 404 |
| 组织 | 跨团队小组成员禁止；停用小组禁止新任务；移出成员遇到负责中任务返回 409 |
| 项目 | 普通人员只能在所属团队创建；归档项目只读；删除为软删除 |
| 任务 | 负责人必须属于小组；日期合法；状态与完成时间一致 |
| 甘特图 | 无开始时间虚拟渲染；拖拽后写入真实开始时间；并发冲突返回 409 |
| Worker | `wrangler dev` 本地通过；D1 migration 可本地和远端应用；无 Node 原生模块依赖 |
| OpenAPI | `api-docs.yaml` 能通过 lint 并导入 Swagger UI / Apifox |
