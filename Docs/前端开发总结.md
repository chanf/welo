## 2. 本次开发目标

本次开发以 `frontend-prototype/index.html` 中的高保真原型为视觉基础，将静态演示页面升级为可以连接真实后端的前端工程。

目标包括：

1. 保留高保真原型的视觉风格和核心交互气质；
2. 将登录、团队、项目、任务、甘特图、工作台和超管后台改为真实数据驱动；
3. 按《前端接入说明》接入后端统一响应、错误码、分页和会话规则；
4. 建立正式前端工程的基础构建、环境变量、格式化和验证流程；
5. 处理权限、空状态、加载失败、并发冲突和移动端可用性问题；
6. 不再依赖 mock 数据、假成功提示或写死的前端演示状态。

当前前端主流程已经达到正式项目可用水平，后续可以在此结构上继续拆分模块和补充自动化回归。

## 3. 工程化建设

### 3.1 工程结构

前端工程位于 `frontend-prototype/`，核心文件如下：

| 文件 | 用途 |
| --- | --- |
| `index.html` | 应用入口、基础视觉样式和挂载点 |
| `app.js` | 页面渲染、状态管理、路由和交互逻辑 |
| `api.js` | 统一 API 请求层和接口封装 |
| `production.css` | 正式页面补充样式和响应式布局 |
| `vite.config.js` | Vite 开发服务器和 API 代理配置 |
| `.env.example` | 环境变量示例 |
| `README.md` | 前端本地开发和验证说明 |
| `.gitignore` | 前端构建产物和本地环境文件忽略规则 |
| `.prettierignore` | 格式化忽略规则 |

### 3.2 构建与环境

- 使用 Vite 管理开发服务器和生产构建；
- 使用 ES Module 组织前端代码；
- API 基础地址来自 `VITE_API_BASE_URL`，没有写死在业务组件中；
- 开发代理默认指向 `http://localhost:8787`；
- `/api/v1` 和 `/health` 通过 Vite 代理转发；
- 代理规则使用 `^/api/`，避免把前端模块 `/api.js` 误转发给 Worker；
- `API_PROXY_TARGET` 可覆盖本地后端地址。

前端脚本：

```bash
npm run dev
npm run build
npm run preview
npm run format
npm run format:check
npm test
```

仓库根目录也提供统一脚本：


## 4. API 请求层

统一请求层位于 `frontend-prototype/api.js`。

### 4.1 请求规则

- 所有业务请求统一经过 `apiFetch`；
- 使用 `credentials: include` 发送 HttpOnly Cookie；
- 自动设置 `Accept: application/json`；
- 有请求体时自动设置 `Content-Type: application/json`；
- API 地址统一拼接 `/api/v1`；
- 查询参数自动过滤空值；
- 请求默认设置 20 秒超时。

### 4.2 响应规则

成功响应按以下结构解析：

```json
{
  "data": {},
  "meta": {
    "requestId": "req_xxx",
    "pagination": null
  }
}
```

请求层会校验响应中是否存在 `data` 字段，避免把异常 HTML 或非标准 JSON 当成业务数据处理。

### 4.3 错误处理

新增 `ApiRequestError`，保留：

- 用户可读错误信息；
- HTTP 状态码；
- 后端错误码；
- 字段校验详情；
- `requestId`。

统一处理的错误场景包括：

- 网络不可用；
- 响应格式异常；
- 业务请求失败；
- 登录失效；
- 权限不足；
- 数据冲突；
- 版本冲突；
- 参数校验失败。

真实业务错误不会被 mock 数据吞掉。全局 401 会清理状态并回到登录页；普通登录凭证错误只提示错误，不触发全局会话清理。

- 停用小组不能用于新任务。

### 5.7 乐观并发控制

任务编辑提交 `expectedUpdatedAt`。

当后端返回 `VERSION_CONFLICT` 时，前端会：

1. 重新拉取任务最新数据；
2. 更新本地保存闭包中的版本号；
3. 保留用户已经输入的表单内容；
4. 提示任务已被其他请求更新；
5. 用户再次确认保存时使用最新版本提交。

这样可以避免静默覆盖其他人的修改，也不会让用户在冲突后重新填写全部表单。

## 6. 前端安全与可用性

### 6.1 安全处理

- API 返回文本插入 HTML 前统一转义；
- 属性中的动态值同样转义；
- 不在前端保存会话 token；
- 不输出密码哈希、会话令牌等敏感字段；
- 请求错误保留 `requestId`，便于后端日志追踪；
- 权限控制不只依赖隐藏按钮，后端 403 会正常提示；
- 删除项目要求输入项目名称确认。

### 6.2 可用性处理

- 表单使用原生必填和长度约束；
- 弹窗使用原生 `<dialog>`；
- 保存中禁用表单按钮，避免重复提交；
- 分页按钮在首页、末页不可继续点击；
- 加载失败提供重试按钮；
- 空团队、空项目、空任务、空小组成员均有明确状态；
- 长文本支持换行或省略，避免破坏表格结构；
- 表格在窄屏下横向滚动；
- 甘特图在窄屏下独立横向滚动；
- 移动端不依赖被隐藏的侧边栏导航；
- 图标按需引入，避免打包完整图标库。

## 8. 后端协同调整

为保证前端正式接入，后端同步做了少量必要调整：

1. 新增小组成员查询接口：

   ```http
   GET /api/v1/teams/{teamId}/groups/{groupId}/members
   ```

2. 任务 `createdAt` 和 `updatedAt` 统一输出 ISO 时间；
3. 任务更新版本号使用单调递增时间，避免同一毫秒连续更新导致乐观锁异常；
4. 修正项目列表在普通成员同时使用搜索和状态筛选时的参数绑定顺序；
5. 任务 DTO 中内嵌小组补充正确的 `teamId`、描述和成员数量；
6. OpenAPI 文档补充小组成员查询契约；
7. 《前端接入说明》同步补充小组成员查询行为。

## 11. 当前边界

当前仍有一定优化空间：

1. 浏览器验收流程尚未沉淀为仓库内可重复执行的 Playwright 测试；
2. `app.js` 承担了路由、渲染、状态和交互，后续应拆分为多个模块；
3. 缺少普通成员、团队管理员和超级管理员的完整多角色自动化用例；
4. 任务列表暂无批量状态修改；
5. 甘特图小时视图的密集表头、今日标线和冲突提示还可以继续增强；
6. 团队管理当前强依赖系统超级管理员，后续可结合后端引入团队管理员模型；
7. 前端尚未配置独立 CI 流水线。
