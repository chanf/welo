# Welo 用户留言功能设计

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |
| 撰写日期 | 2026-09-14 |
| 目标版本 | V1 |
| 适用页面 | 登录 / 注册页（未登录状态） |
| 通知渠道 | Telegram Bot |

## 1. 设计目标

在用户尚未登录的登录 / 注册页提供留言入口，让访客可以直接把问题或建议提交给 Welo 团队。一期只做单向留言通知，不提供站内留言列表、状态跟踪、管理员后台或 Telegram 双向回复。

后端负责字段校验、基础防滥用和 Telegram 转发。留言正文不落库，浏览器不接触 Telegram Bot Token。

## 2. 前端交互

### 2.1 入口

登录页和注册页共用同一个认证界面。在认证表单下方放置一个次级按钮：`用户留言`。

交互要求：

1. 点击后打开当前应用已有的模态框，不跳转页面；
2. 登录模式和注册模式都能进入留言；
3. 弹窗关闭后焦点返回原入口按钮；
4. 提交过程中禁用全部按钮，防止重复提交。

### 2.2 表单字段

| 字段 | 中文名 | 必填 | 校验 |
| --- | --- | --- | --- |
| `nickname` | 用户昵称 | 是 | 去除首尾空白后 1-64 个字符 |
| `contact` | 联系方式 | 是 | 去除首尾空白后 3-128 个字符 |
| `message` | 留言内容 | 是 | 去除首尾空白后 1-1024 个字符 |

联系方式不限定格式，允许邮箱、手机号、微信号或其他联系方式。服务端必须执行与前端一致的长度和必填校验。

### 2.3 状态提示

| 状态 | 文案 | 行为 |
| --- | --- | --- |
| 提交中 | 按钮显示 `发送中` | 禁用提交和关闭按钮 |
| 成功 | `留言已发送` | 关闭弹窗并清空本次内存中的表单值 |
| 失败 | 显示后端错误信息 | 保留弹窗和用户输入，允许重试 |
| 限流 | `留言提交过于频繁，请稍后再试` | 保留用户输入 |

## 3. API 设计

```http
POST /api/v1/public/feedback
Content-Type: application/json
```

请求体：

```json
{
  "nickname": "张三",
  "contact": "zhangsan@example.com",
  "message": "希望增加……"
}
```

成功响应：

```json
{
  "data": {
    "status": "sent"
  }
}
```

成功状态码为 `201`。

错误沿用现有 API 响应结构。主要错误：

| 状态码 | code | 说明 |
| --- | --- | --- |
| 400 | `VALIDATION_ERROR` | 字段缺失、为空或超过长度限制 |
| 429 | `RATE_LIMITED` | 同一来源提交过于频繁 |
| 503 | `TELEGRAM_UNAVAILABLE` | Telegram 配置缺失或发送失败 |

该接口是公开接口，必须注册在全局 `authRequired` 中间件之前，不读取登录会话，也不把访客与用户账号关联。

## 4. Telegram 通知

### 4.1 Bot 配置

| 配置 | 类型 | 说明 |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | Worker secret | BotFather 创建 bot 后获得的 token |
| `TELEGRAM_FEEDBACK_CHAT_ID` | Worker secret | 接收留言的个人聊天、群组或频道 chat id |

这两个值都不能写入 `wrangler.jsonc`、前端环境变量或仓库文件。生产环境使用 `wrangler secret put` 配置；本地开发写入被忽略的 `.dev.vars`。

### 4.2 发送接口

后端调用：

```http
POST https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/sendMessage
Content-Type: application/json
```

请求体：

```json
{
  "chat_id": "<TELEGRAM_FEEDBACK_CHAT_ID>",
  "text": "Welo用户留言：\n用户昵称：张三\n联系方式：zhangsan@example.com\n留言内容：希望增加……"
}
```

消息必须以固定前缀开头：

```text
Welo用户留言：
```

随后按顺序输出三个字段。发送时使用纯文本，不设置 `parse_mode`，因此用户输入中的 HTML 或 Markdown 符号不会被 Telegram 解析。

Telegram 响应满足 `ok: true` 才视为发送成功。发送失败时不返回内部 token、chat id 或 Telegram 原始错误，统一对外返回 `TELEGRAM_UNAVAILABLE`。

## 5. 防滥用与隐私

公开接口可能被脚本刷屏，一期使用 D1 做轻量限流：

1. 从 `CF-Connecting-IP` 获取客户端 IP；
2. 仅保存带业务前缀的单向 SHA-256 标识，不保存原始 IP；
3. 同一来源最近 1 分钟最多 1 条，最近 1 小时最多 5 条；
4. 限流记录不包含昵称、联系方式或留言正文；
5. 过期记录由既有 Cron Trigger 清理。

一期不保存留言内容。若 Telegram 最终发送失败，接口返回失败，由用户稍后重试。应用日志不得输出留言内容、Bot token 或 chat id。

## 6. 数据结构

新增 D1 表只用于限流，不存储业务留言：

```sql
CREATE TABLE feedback_rate_limits (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ip_hash TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX idx_feedback_rate_limits_ip_created
  ON feedback_rate_limits (ip_hash, created_at);
```

## 7. 验收清单

1. 登录页和注册页均可见 `用户留言` 入口；
2. 三个字段为空时无法提交，浏览器与服务端都会拦截；
3. 留言内容超过 1024 个字符时无法提交；
4. 成功提交后 Telegram 收到以 `Welo用户留言：` 开头的纯文本消息；
5. 昵称、联系方式或留言内容包含 `<b>`、反引号、链接等字符时不影响消息展示；
6. 同一 IP 1 分钟内提交第二条返回 429；
7. 缺少 Telegram secret 时接口返回 503，且不暴露 secret；
8. 后端类型检查和前端生产构建通过。
